# Contract gaps

`packages/contracts` stays the source of truth, and this phase does not change it. Where the API needed a shape the contracts do not define, it uses the safest compatible transport boundary: every field inside such a shape reuses its contract definition, and responses that are contract types are validated against the committed schemas. Each gap below proposes a change for the integration branch.

| # | Gap | Transport boundary used now | Proposed contract change |
|---|---|---|---|
| 1 | No request contract for creating a draft. `RecoveryRecord` requires server-owned fields (`human_reference`, `qr_payload`, `revision`, `sync`, states) and an `original_image_evidence_id` that cannot exist before the photograph is stored. | `POST /v1/recovery-records`, multipart: `record` = `RecoveryRecordDraftCreate` (composed from `RecoveryRecord` field schemas plus original-photo provenance), `original_image` = file. | Add `RecoveryRecordDraftCreateSchema` (client-supplied fields + `EvidenceUploadProvenance`) and a documented multipart binding. |
| 2 | No request contract for editing a draft. | `PATCH /v1/recovery-records/{id}` with `RecoveryRecordDraftUpdate` (same field schemas, nullable where optional) and `If-Match: "<revision>"`. | Add `RecoveryRecordDraftUpdateSchema` and state that `revision` is the concurrency token (ETag). |
| 3 | `DestinationSelection` lets the client assert `facility_type` and `verification_status`. | The client sends `destination_location_id` only; the server fills type, status and time from the directory. | Split `DestinationSelectionRequest` (location ID) from the server-populated `DestinationSelection`. |
| 4 | No contract for the submission result. The web port returns `submitted` or `duplicate_image`. | `{outcome, record, replayed, flag_codes}` in the success envelope. | Add `RecordSubmissionResponseSchema` (discriminated by `outcome`). |
| 5 | No list/page contract for records, evidence or timelines. `CursorPaginationMeta` exists, but no page wrapper. | `{items: RecoveryRecord[], pagination: CursorPaginationMeta}`; evidence lists and timelines are plain arrays of `Evidence` / `RecoveryRecordEvent`. | Add a generic `pageSchema(item)` and list-filter request schemas. |
| 6 | No evidence upload contract. `Evidence` is a stored-metadata shape. | Multipart `image` + fields from `Evidence`/`Provenance` (`EvidenceUploadFields`). | Add `EvidenceUploadRequestSchema` and name the server-generated evidence types. |
| 7 | Server-generated evidence (QR scan, recycler receipt, reviewer decision) needs a `device_instance_id`, and `Provenance` has no concept of the server as capturer. | `capture_source: system_generated`, fixed server device-instance ID `0199c0de-0000-7000-8000-000000000001`, `application_version` = API version. | Allow `device_instance_id` to be absent for `system_generated`, or add a `ServerInstanceId`. |
| 8 | `Provenance` cannot say that EXIF/metadata was stripped by re-encoding, so `content_digest` covers the stored (sanitised) bytes, not the uploaded bytes. | Recorded in `evidence.metadata_stripped`; the digest is of the stored object. | Add `storage_transform: "reencoded_without_metadata"` and optionally `original_upload_digest`. |
| 9 | Review flag codes and reviewer reason codes are free strings in the contracts. | The exact codes the web domain layer already uses (`apps/web/src/services/domain/flags.ts`) are enforced server-side. | Move `REVIEW_FLAG_CODES`, `REVIEW_REASON_CODES` and `REASON_CODES_BY_DECISION` into `packages/contracts`. |
| 10 | Actors hold at most one role. ADR-006's multi-role policy is undecided. | An account with more than one distinct role cannot sign in. | Decide multi-role and delegation policy; add `active_role` to the session contract if needed. |
| 11 | No authentication/session contract. | `POST /v1/auth/sessions` → `{access_token, token_type, expires_at, user}`; `GET /v1/auth/me` → `CurrentUser`. | Add `SessionSchema` / `CurrentUserSchema` (web `Session` port) once an identity ADR exists. |
| 12 | `RecoveryRecord.sync` is client-oriented; the server has no offline state for its own copy. | Server representations report `sync_state: synchronized` and `local_revision = server_revision = revision`. | Document that `sync` on a server response describes the canonical copy. |
| 13 | No contract for QR lookup. The web port's `HandoffLookupResult` embeds a full `RecoveryRecord`, which would disclose coordinates and prediction detail before acceptance. | `POST /v1/handoff-lookups` with exactly one of `qr_payload`, `qr_text`, `lookup_token` or `transfer_code` → `{outcome: ready\|not_ready\|already_received\|other_facility, record?: HandoffPreview, received_at?, lookup_token?}`. Unknown codes → `404`; unsupported version → `422 UNSUPPORTED_CONTRACT_VERSION`. | Add `HandoffLookupRequestSchema`/`HandoffLookupResponseSchema` with a minimised `HandoffPreviewSchema`. |
| 14 | `HandoffRequest` requires `lookup_token`, but a recycler who types the transfer code (FR-HND-001) has no token. | A successful `ready` lookup returns the current `lookup_token` to the authorised, facility-scoped recycler. | Make the token optional when the request carries a verified transfer-code lookup, or bind a short-lived lookup session. |
| 15 | `HandoffResponse.rejected` has no defined reason codes, and the web adapter treats a token mismatch as `rejected`. | Invalid or mismatched tokens return `404` (no existence oracle). `rejected` is used only for `RECORD_NOT_AWAITING_HANDOFF`, returned with HTTP 200 as a domain outcome. | Enumerate `reason_code` values and state which failures are envelopes rather than outcomes. |
| 16 | Handoff `notes` are not in `HandoffRequest` (the web form collects them). | Not accepted; unknown fields are rejected. | Add optional `notes` (max 1,000) if the product still needs it. |
| 17 | Lookup-token issuance, expiry and rotation are undefined (ADR-004 follow-up). | Created inert with the draft, activated on `publish_for_handoff`, `SCRAPTRACE_QR_TOKEN_TTL_DAYS` expiry, owner rotation via `POST /v1/recovery-records/{id}/qr-token-rotations`, `used_at` at handoff. | Record the policy in an ADR and add a `QrTokenStatus` if clients need to show expiry. |
| 18 | No contract for editable processing drafts or material-entry editing; `ProcessingRequest` is a single final submission. | `PUT /v1/recovery-records/{id}/processing` (`ProcessingDraftUpdate` with `ProcessingRequest` field names), `POST/PATCH/DELETE …/processing/material-entries[/{entry_id}]` → `ProcessingDetail`. The submitted `ProcessingRequest` is authoritative and replaces draft entries. | Add `ProcessingDraftSchema` and `MaterialEntryWithIdSchema`, or document that drafts are client-local. |
| 19 | `ProcessingRequest.notes` is optional (≤1,000), but `ProcessingInformation.result` is required (≤500). | `notes` is required on submission; `result` holds its first 500 characters and the full notes are stored. | Add an explicit `result` field to `ProcessingRequest`, or align the limits. |
| 20 | No rule for recovered totals or missing material weights. | Web-domain flags reused: `PROCESSED_WEIGHT_ABOVE_RECEIVED` when recovered weight exceeds received weight, `MISSING_MATERIAL_WEIGHTS` for `material_recovery` without entries. Both are review flags, not rejections. | Put the processing flag rules and codes in `packages/contracts`. |
| 21 | No contract for review cases or queue items. | `ReviewCaseSummary` (case ID, record ID, reference, category, status, flags, opened time, facility, assignee, record state, `decision_eligible`, latest decision) and a case detail combining `RecoveryRecord`, `Evidence[]`, `RecoveryRecordEvent[]` and decision views. | Add `ReviewCaseSchema` and `ReviewQueueFiltersSchema`. |
| 22 | `ProgrammeReviewRequest` carries `previous_*_state` and a client `decision_timestamp` with no stated semantics. | Previous states act as an optimistic-concurrency check (`409 VERSION_CONFLICT` on mismatch). The client timestamp must fall between case opening and now; server `recorded_at` is stored separately. Idempotency operation must be `review_<decision>` (web) or `record_review_decision` (sync mutation type). | Document these semantics and fix one idempotency operation name per command. |
| 23 | Reviewer-initiated `flag_for_review` (`review:flag`) has no request contract. | Not exposed; flags are raised by server rules only. | Add a `FlagForReviewRequestSchema` if reviewers need to flag records manually. |
