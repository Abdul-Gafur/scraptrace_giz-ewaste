# Phase 1 integration reconciliation

This document records the merged baseline at `3003ba2` and is the checklist for the five
integration milestones. The backend and frontend feature tips (`156287e` and `79de9d5`) are both
ancestors of the integration branch. The merge commits contain no manual conflict-resolution
hunks, and the initial worktree was clean.

## Baseline

- Node: 20.20.2; npm: 10.8.2; Python: 3.11 (repository-local `.venv`).
- PostgreSQL: the development service in `apps/api/compose.yaml` (PostgreSQL 16).
- API: FastAPI under `/v1`, 34 application operations plus three health operations.
- Web: Next.js 16.3.5; `NEXT_PUBLIC_API_MODE=http` selects the HTTP adapter.
- Contracts: Zod is authoritative; committed JSON Schemas are generated from the registry.
- Vision: `services/vision/checkpoints/best_model.pth` and its checksum-bearing manifest are
  present.

The first baseline command attempt failed before collection because dependencies were not
installed. This is an environment precondition, not a product failure. After `npm ci` and creation
of the Python 3.11 virtual environment, the same commands are used for the reproducible baseline.

## Contract-gap disposition

|   Gap | Disposition                        | Reason / target                                                                                                                              |
| ----: | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
|   1–9 | Accept and resolve now             | Draft, list, evidence, submission, provenance, and review-code gaps cross active Phase 1 boundaries.                                         |
|    10 | Defer to Phase 2                   | Multi-role/delegation policy is a product and identity decision; Phase 1 demo accounts intentionally have one role.                          |
|    11 | Accept and resolve now             | Browser session parsing is an active shared boundary. Public auth contracts exclude password and token internals where not required.         |
|    12 | Accept as documentation correction | A server record's sync fields describe the canonical synchronized copy; no offline sync state is implied.                                    |
| 13–15 | Accept and resolve now             | Lookup preview, credential separation, and rejection semantics are required for the QR/manual flows.                                         |
|    16 | Accept and resolve now             | The handoff form captures notes; cap them at 1,000 characters in the shared request.                                                         |
|    17 | Accept and resolve now             | Issue/expiry/rotation/revocation state is needed by current QR screens and security tests.                                                   |
| 18–22 | Accept and resolve now             | Durable processing drafts, material rows, weight rules, review queue/detail/filtering, outcome naming, and concurrency are active workflows. |
|    23 | Reject for Phase 1                 | No current UI or requirement needs arbitrary reviewer-created flags; server rules open cases. Adding it would expand scope and audit policy. |

Frontend-reported gaps are covered by the corresponding rows above. Upload byte-level progress is
rejected as a defect because Fetch has no portable progress API and pending/error feedback satisfies
Phase 1. The missing inference-duration field is also rejected: the model contract promises an
inference timestamp, not a fabricated duration. Everything else affecting an implemented workflow
is accepted for the following milestones.
