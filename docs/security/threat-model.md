# Threat model

## Scope and status

This initial register covers the proposed mobile web, API, vision, safety assistant, evidence storage, offline state, recycler workflow, dashboard, and software supply chain. No listed control is implemented; every control has status **Proposed**. Likelihood/severity scoring awaits architecture, deployment, user research, and programme decisions.

## Assets and trust boundaries

Key assets are identity/roles, recovery evidence, images/location, measurements, review/audit history, safety content, model/dataset/prompt artefacts, provider credentials, future financial instructions, and programme reports. Trust boundaries include phone/browser storage, public network/API, object storage/database, service-to-service calls, recycler/programme actors, AI providers, map/providers, build/dependencies, and administrative access.

## Assumptions and exclusions

The register assumes no current implementation and therefore does not assess concrete endpoints, cloud configuration, cryptography, or runtime. Social engineering, physical facility safety, recycler certification, scale calibration, and regulatory fraud require programme/operational controls beyond software. Mobile-money and government threats require separate models if those future integrations are authorised.

## Review process

Update the register when architecture, data fields, roles, providers, offline mode, model/task, upload design, deployment, or programme rules change; after incidents or tests; and before pilot/production. Each threat should later receive owner, likelihood, impact, test/evidence, target date, accepted residual risk, and review date. Security and privacy owners approve risk acceptance with affected product/programme owners.
